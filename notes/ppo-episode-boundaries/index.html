Bootstrapping at Episode Boundaries in PPO

Termination, truncation, and why GAE needs two different masks.

Intro

When reading about PPO, it’s easy to focus on the clipped objective and skim over how the advantages are computed. This note looks at one small part of that bookkeeping: what happens when an episode stops because we ran out of collection time, rather than because the task actually ended?

I’ll start with bootstrapping, work through how episode boundaries enter GAE, and then put the two masks into code. The main question is when to keep the final state’s value estimate, even though we’re about to reset the environment.

What does “done” actually mean?

In a PPO rollout, an episode ending feels like it should be one boolean. The environment says it’s done, we reset it, and move on. But there are two questions hiding in that one flag: should we estimate any reward after the last state, and should we keep accumulating advantages from the next transition?

These questions can have different answers. That’s the detail I want to work through here. This note follows the time-limit discussion in Pardo et al. [1] and Gymnasium’s explanation of its step API [2], with PPO and GAE as the setting.

The short version: a time-limit reset can stop the trajectory without making the last state worthless. Slightly annoying distinction, but it matters :)

Why bootstrap in the first place?

PPO collects a finite batch of experience before updating its policy [3]. Usually we haven’t observed every future reward from every state in that batch. A value function gives us an estimate of the part we didn’t get to see.

\[ V^\pi(s_t)=\mathbb{E}_\pi\!\left[\sum_{k=0}^{\infty}\gamma^k r_{t+k}\,\middle|\,s_t\right]. \]

Here, \(r_t\) is the reward on the transition from \(s_t\) to \(s_{t+1}\), and \(0\leq\gamma<1\) is the discount factor. For episodic tasks, take rewards after termination to be zero. We’ll use \(V\) for the critic’s current estimate, held fixed while computing targets.

A one-step target is then

\[y_t=r_t+\gamma V(s_{t+1}).\]

This is bootstrapping: using the critic to estimate the unobserved future. It lets us learn from partial trajectories, although an inaccurate critic also introduces error. GAE combines several such temporal-difference residuals to control the bias–variance tradeoff [4].

Termination vs. truncation

Termination is an ending defined by the task: reaching a goal, failing, or hitting a deadline that is actually part of the objective. There are no future task rewards after that transition, so the bootstrap term is zero.

Truncation is an external cutoff. Imagine collecting 1,000 steps of a continuing robot-control task and resetting to gather more varied experience. The data stops there, but the task’s return would have continued from that final state. We still bootstrap.

Gymnasium exposes these separately [2]:

next_obs, reward, terminated, truncated, info = env.step(action)
episode_ended = terminated or truncated

episode_ended is useful for deciding to reset. It doesn’t contain enough information to decide the value target.

One caveat before going further: a deadline can be a real termination. If the task is “score as much as possible in 60 seconds,” the clock belongs to the task. For a Markov observation, the policy also needs the remaining time. “Always bootstrap at a time limit” would be the wrong rule here [1].

Where this enters GAE

Let \(z_t\) indicate termination and \(u_t\) indicate truncation on transition \(t\). For collected data that resets after either event, define two masks:

\[ b_t=1-z_t,\qquad c_t=1-\mathbb{1}[z_t\lor u_t]. \]

\(b_t\) controls bootstrapping. \(c_t\) controls whether the GAE trace continues into the next stored transition. They answer the two questions from the intro.

With boundary handling made explicit, the TD residual is

\[ \delta_t=r_t+\gamma b_tV(s_{t+1}^{\mathrm{final}})-V(s_t), \]

where \(s_{t+1}^{\mathrm{final}}\) means the actual successor of this transition, before any reset. On an ordinary step, it’s just the next observation. GAE’s backward recurrence becomes

\[ \hat A_t=\delta_t+\gamma\lambda c_t\hat A_{t+1}. \]

Inside an uninterrupted trajectory, expanding this gives the familiar weighted sum of residuals [4]:

\[ \hat A_t=\delta_t+\gamma\lambda\delta_{t+1} +(\gamma\lambda)^2\delta_{t+2}+\cdots. \]

At a truncation, we keep the next-state value inside \(\delta_t\), but stop the recurrence there. Otherwise \(\hat A_{t+1}\) could belong to a completely different episode. Keeping that value and stopping that trace are both necessary.

A small example

Suppose \(r_t=1\), \(\gamma=0.99\), \(V(s_t)=8\), and \(V(s_{t+1}^{\mathrm{final}})=10\). We’ve reached an external time limit and will reset.

\[ \begin{aligned} y_t^{\mathrm{trunc}}&=1+0.99(10)=10.9,\\ \delta_t^{\mathrm{trunc}}&=10.9-8=2.9. \end{aligned} \]

If we use 1 - done for bootstrapping, we get \(y_t=1\) and \(\delta_t=-7\). Same observed transition, opposite sign. At this boundary \(c_t=0\), so the advantage equals that residual.

That can affect the policy update too: before any advantage normalization, PPO sees a positive advantage in one case and a negative one in the other. Its clipped objective uses those advantages; clipping doesn’t fix how they were computed [3].

How far does the mistake travel?

For this truncation, zeroing the bootstrap changes the residual by

\[ \Delta\delta_t =\delta_t^{\mathrm{wrong}}-\delta_t^{\mathrm{correct}} =-\gamma V(s_{t+1}^{\mathrm{final}}). \]

Holding the critic and all other residuals fixed, the difference propagates backward through the same episode:

\[ \Delta\hat A_{t-k} =(\gamma\lambda)^k\Delta\delta_t. \]

For \(\lambda=0.95\), the error one transition earlier is \(0.9405(-9.9)=-9.31095\). So this isn’t confined to the final action. If the final-state value is negative, the error reverses direction; it isn’t universally a downward bias. These numbers are a toy calculation, not a training result.

A minimal implementation

Here’s the bookkeeping for one environment’s rollout. All arrays have length \(T\). next_values[t] is evaluated on the actual successor observation of transition t, including the final pre-reset observation at truncations.

def compute_gae(rewards, values, next_values,
                terminated, truncated, gamma=0.99, lam=0.95):
    advantages = [0.0] * len(rewards)
    gae = 0.0

    for t in reversed(range(len(rewards))):
        bootstrap = 0.0 if terminated[t] else 1.0
        continue_trace = 0.0 if (
            terminated[t] or truncated[t]
        ) else 1.0

        delta = (
            rewards[t]
            + gamma * bootstrap * next_values[t]
            - values[t]
        )
        gae = delta + gamma * lam * continue_trace * gae
        advantages[t] = gae

    targets = [a + v for a, v in zip(advantages, values)]
    return advantages, targets

Initializing gae = 0 stops the recurrence at the end of this batch. We still include its last transition’s bootstrap value. In a tensor implementation, compute these targets without gradients and keep an independent trace for each vectorized environment. Only actual environment transitions belong in these arrays; exclude reset-only steps if your next-step autoreset mode produces them [6].

The value target here is \(\hat R_t^{\lambda}=\hat A_t+V(s_t)\). Construct it using the unnormalized advantages. If you normalize advantages for PPO’s policy loss, do that afterward.

The autoreset gotcha

Some vector environments return a reset observation in the same call that reports an episode ending. In that case, blindly evaluating V(next_obs) bootstraps from the beginning of a new episode. We need the final observation of the old one.

Exactly where that observation lives depends on the wrapper and autoreset mode. Check the API you’re actually using, rather than assuming one particular info key works everywhere. Gymnasium documents its modes separately [6].

You might also see implementations add \(\gamma V(s_{t+1}^{\mathrm{final}})\) to a truncated transition’s stored reward, then use a single episode-end mask. That can encode the same correction. Don’t add it to the reward and bootstrap it again.

What to check when reading PPO code

The PPO implementation-details article is useful here because it distinguishes reproducing a particular implementation from choosing the theoretically appropriate time-limit handling [5]. For a new implementation, I’d trace these three things:

  • Does the bootstrap mask use terminated, or does every reset zero the value?
  • Does the GAE recurrence stop before the next episode’s residuals?
  • At an autoreset, which observation actually goes into the critic?

For an external cutoff followed by a reset, the combination is: keep the final-state value, stop the advantage trace. Two masks, two jobs. That’s the part worth keeping next to the code :)
